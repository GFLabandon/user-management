## 4D.1：安全处置要有边界

当前 MySQL 阻断项来自 Python 包及 `gosu` 内嵌的 Go 标准库。应按组件来源和运行用途分类，避免把全部扫描项误认成业务 Java 代码问题。

1. 核对官方同系列镜像是否有新构建及相关上游公告，记录候选 digest、平台、组件版本和修复依据。方案不预先指定一个未经验证的替代版本。
2. 优先验证官方修补后的镜像。固定 digest 能保证构建使用相同内容，但不会自动获得上游补丁，因此更新 digest 必须伴随重建和验收。[Docker 官方构建建议](https://docs.docker.com/build/building/best-practices/)
3. 若官方镜像仍有问题，记录组件是否实际参与启动或业务路径以及判断依据；不能仅凭“没主动调用”认定不受影响，也不能把扫描器的修复版本直接当作当前镜像可安装的版本。
4. 只有在修复来源、构建方式和后续维护成本清楚时，才评估小范围派生镜像。不能为了扫描变绿，直接删除未知用途的软件包、替换数据库产品或批量忽略告警。
5. 没有低成本、可验证的修复方案时，明确写“发布阻断，等待上游／待进一步处置”，结束本轮核对，转入本地 5A。任何例外规则必须单独评审，不在本计划中默认放行。

镜像变更后，执行 Java/Python 检查、三套真实 MySQL 验收和完整扫描，并保存对应远程 CI 链接。顺带核对工作流已有的 Actions 运行时弃用提示；如需更新，独立提交并按官方兼容说明验证，不与业务改动混在一起。

## 5A：先让现有业务更好用

### 5A.1 账号关联档案

将数字输入框改成按工号或姓名搜索的选择控件，候选项展示“姓名、工号、院系”，明确当前选择并允许取消关联；账号列表同步显示可读的档案信息。

只返回有限条数的候选结果，复用当前模板和轻量交互，不加载整张档案表。新增查询入口只向有账号管理权限的用户开放；服务端继续检查档案存在性、唯一关联约束和账号版本，前端选择不能代替后端校验。搜索结果只包含选择所需字段。

验收：同名可区分、无结果有提示、编辑时正确回显；伪造档案 ID、重复关联和两个管理员同时操作均有明确反馈；只读用户不能访问管理搜索或修改关联。表单校验失败保留非敏感输入，不回填密码。

### 5A.2 错误与失败提示

统一处理参数错误、无权限、页面不存在、上传过大和内部错误，保留正确的 HTTP 状态码；区别登录失效、CSRF 失败、业务约束和编辑冲突。失败页面给出可执行的返回或重新登录入口，必要时显示可用于查日志的请求编号。

优先处理上传校验、档案编辑冲突、账号停用和密码重置相关路径。通用页面不显示堆栈、SQL、文件绝对路径、密码或会话信息。安全过滤器和 multipart 层的失败也要覆盖，不能只验证 Controller 抛出的异常。

验收：用户能知道下一步怎么做；拒绝的请求不会修改数据；已有“至少保留一个启用管理员”、CSRF 和旧会话失效机制不回退。

### 5A.3 操作记录查询

先补动作、对象、结果的中文说明，再增加操作者、对象类型／编号、时间范围和结果筛选及分页。底层事件代码保留稳定，不改写历史记录；未知代码有安全的显示兜底。

查询参数必须绑定，排序字段采用固定规则，限制每页条数；日期范围和时区在页面上说明。默认按记录 ID 倒序，翻页时保留筛选条件。不在本轮增加批量导出和统计大屏。

验收：超过 100 条记录仍可查到早期事件；空结果、非法时间范围、页码越界有合理反馈；筛选与总数一致；只读用户不能越权查看审计内容。

## 5B：围绕文件与事务做局部重构

先列出并验证“文件写入失败、数据库提交失败、提交后旧图删除失败、重试时文件仍被引用”四类场景。只有实际职责混杂阻碍错误处理时，才抽取应用服务；不为了目录整齐增加空接口和通用基类。

最低交付是清楚的失败记录和可控的补偿入口。若确实需要跨重启自动重试，再引入持久化清理任务：记录受控文件标识、状态、尝试次数和下次执行时间，设置重试上限，重复执行安全。旧图任务要与成功的档案更新建立一致关系；事务回滚后产生的孤立新文件需单独处理，不能把补偿任务一起回滚后就当作已经解决。

删除前重新检查引用，限制在上传根目录和允许的文件名范围内，并处理检查与删除之间的竞争。无法可靠确认可以删除时，保留文件并记录待核查项。当前是单实例，暂不引入 Redis、消息队列或分布式锁。

如果新增 V5 清理任务表，必须一并更新 `scripts/maintenance.py` 的表集合、迁移历史校验、备份清单格式及版本兼容规则，补新库迁移、旧库升级和新旧备份的恢复验证。V1–V4 不修改。不能只加表让应用通过测试，却破坏现有备份工具。

## 6：出现瓶颈后再优化性能

先用合成数据建立小、中、大三档查询基线，记录数据量、硬件、数据库版本、查询条件、执行计划、SQL 数量和重复测量耗时，再判断是否需要索引、调整查询或改变深分页方式。合成数据不能包含真实师生资料。

优先看档案筛选和操作记录查询。新增索引必须有对应查询及前后对照，同时检查写入影响；如果现有响应足够稳定，就保留现状。没有测量依据时不增加缓存、不提前拆服务，也不写“支持高并发”。

## 提交与收尾

每个批次使用一个短期 `codex/` 分支；同一批次按独立行为拆成可验收提交，合并后只删除已确认合并且无独有成果的分支。开始实施前重新同步并检查远程差异，本文的基线状态不保证未来没有冲突。

页面改动执行相关 Web、权限和表单测试，并实际检查页面；SQL、事务或文件改动补对应真实 MySQL 验收；镜像、迁移和备份变更执行完整相关验收。纯文档改动只做差异与链接检查，避免为凑测试数量反复跑无关流程。
