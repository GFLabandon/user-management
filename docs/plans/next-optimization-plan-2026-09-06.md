## 4A：部署配置与版本核对

**拟改动**：新增独立部署配置与启动说明，采用集中配置校验。保留本地演示的便利，但部署入口必须明确启用部署配置，校验数据库连接、应用账号、上传目录、首次管理员凭据。拒绝同时激活 `demo`；已有账号库不要求重复提供初始化密码，也不重新设置密码。运行前检查上传目录可写，使用专用数据库账号；后续可将迁移权限与业务权限分开。

**版本核对**：导出真实依赖树，核对官方维护状态和安全公告，记录 JDK、Spring Boot、Spring Security、MyBatis、Flyway、Connector/J 和 MySQL 组合。若需要更新，独立提交兼容性升级并重跑认证、CSRF、迁移与图片测试；此方案不把网页上的“最新版本”当成已经批准的升级目标。

**验收**：缺少数据库参数、意外开启演示配置、不可写上传目录及空账号库缺少首次凭据时，均以清楚且不包含秘密的错误失败；正常空库初始化成功，已有库重启不改账号。部署文档能区分数据库密码、首次管理员密码和后续账号密码。

## 4B：可复现部署与健康检查

**拟交付**：根目录 `Dockerfile`、`.dockerignore`、`compose.yaml`，以及 `docs/guides/deployment.md`。镜像用非 root 运行，构建目录和本机配置不带入镜像；MySQL 数据和头像分别持久化。MySQL 默认只在内部网络提供服务，本地演示的应用端口绑定回环地址；真实公网入口另行配置 HTTPS。

Compose 启动顺序结合数据库健康状态，不能把“容器已启动”当成“数据库可用”；同时保留应用端的连接失败处理。官方说明见 [Compose 启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)。

引入 Actuator 的最小健康检查：分别检查进程存活与业务就绪。数据库暂不可用应影响就绪状态，不应让存活探针造成反复重启。项目已有自定义 `SecurityFilterChain`，因此新增端点要显式配置规则；健康响应不返回凭据、连接串或组件细节，管理端点不整体放开。依据：[Spring Boot Actuator](https://docs.spring.io/spring-boot/3.5/reference/actuator/endpoints.html)。

增加请求关联编号、必要的错误日志和日志轮转；日志不写密码、Session、CSRF token、请求正文或整份档案。使用 HTTPS 时再配置 Secure Cookie 和可信代理边界，不能信任任意来源的转发头。保留当前 Session + CSRF 模型。

**验收**：新环境构建启动；数据库延迟启动、断开及恢复；重建应用容器后账号、档案与头像仍在；健康端点真实反映状态，其他管理端点不可访问；日志可以定位失败且不泄密。初版只保证单实例，不声称支持无损滚动发布或跨实例会话。

## 4C：备份与恢复

2026-09-25 已完成：13 项安全测试、8 组 MySQL 恢复验收；具体命令与边界见[指南](../guides/backup-and-restore.md)。以下保留原验收范围。

**拟交付**：`scripts/backup.sh`、`scripts/restore.sh` 和 `docs/guides/backup-and-restore.md`。脚本先在临时数据库和临时上传目录中演练。

最小方案采用维护窗口：阻止业务写入后，再备份数据库和头像，记录提交号、Flyway 版本、时间、文件清单与校验值。单独执行数据库一致性导出不能保证与磁盘头像处于同一时点；备份流程必须处理这一点。账号哈希同样属于敏感数据，备份应限制访问，凭据不写入参数、日志或仓库。

恢复默认指向新的数据库和空上传目录；发现非空目标即停止，不自动覆盖。核对档案、院系、账号、状态历史、操作记录行数以及头像引用与文件；完成后实际登录、搜索、编辑、读取头像，再确认恢复耗时。依据演练结果制定恢复目标，不提前声称零丢失或固定恢复时间。

**验收**：备份文件缺失或校验不符会明确失败；恢复到独立环境成功；不能仅凭 SQL 导入成功宣布恢复完成。回退应用版本需使用兼容的数据库与文件备份，不能只切 Git 提交。

## 4D：把本机验收变成自动化发布证据

H2 与 Python 安全测试保留为快速反馈；新增独立 MySQL CI 任务，优先复用现有 Compose、`verify-compose.py` 和 `verify-recovery.py`，不另建重复的服务容器或 Testcontainers 流程。CI 先构建待验收应用镜像，再运行随机项目演练；设置超时与失败清理，报告按任务分别上传。测试库一次一建，测试不得连接开发者现有数据库。

至少覆盖：空库 V1–V4、V3 升级、缺失映射拒绝、首次账号配置失败、真实登录与 multipart CSRF、只读伪造写请求、停用账号的旧会话、重启持久化、恢复后的图片读取。不要只用模拟认证和 MockMvc 代替真实 HTTP 验收。

现有 4B／4C 脚本覆盖运行与恢复，仍需单独补真实 MySQL 的旧库升级及缺失映射拒绝验收，不能把空库初始化当作旧库迁移证据。

CI 分开报告单元／Web 测试、MySQL 验收和依赖检查，失败保留脱敏日志。依赖与镜像检查记录工具、数据库更新时间、完整版本与实际发现；复核 Flyway 对当前 H2／MySQL 的验证范围，必要升级单独提交并回归，不以扫描命令成功代替风险结论。新增 `docs/guides/release.md`，列出配置、版本、迁移、备份、验证与回退步骤。只有容器部署、恢复和认证边界都通过后，才安排带虚构数据的 HTTPS 演示；公网开放之前补登录限流并检查依赖风险。

## 5A：操作体验与账号维护

1. 统一 400、403、404、413 和 500 页面，提供返回入口与请求编号；处理无权限、会话过期、上传过大、数据库约束冲突，不向用户展示 SQL 或堆栈。
2. 账号关联档案改为工号／姓名搜索并显示当前选择，不让使用者从网址读取数字 ID。服务端仍检查存在性与唯一关联，不一次加载全部档案。
3. 操作记录增加中文动作和结果、按时间／操作人／对象筛选与分页；只给管理员使用，不在审计里补录密码或完整档案内容。
4. 补清晰的密码重置、账号停用和会话失效提示；保持当前管理员及最后一个管理员保护，扩大权限前先确认真实需求。

**验收**：管理员与只读账号分别验证；无结果、无效输入、停用关联、旧表单冲突都能完成纠正；桌面和手机宽度可操作。新增查询先测 SQL 数量，避免产生新的逐行关联查询。

## 5B：文件清理可靠性

首先补充故障测试：上传写盘失败、数据库提交失败、旧图删除失败、重复重试、路径绕过。解决读取检查与实际打开文件之间的符号链接替换风险时，应从最终文件打开方式入手，保留无引用图片不可访问的限制。

按确实发生的失败引入数据库中的待清理任务：记录目标、原因、重试次数和时间，业务提交后执行；重试前确认没有任何档案引用，严格限制在上传根目录内。任务应幂等，重试耗尽能让管理员知晓。先提供只读巡检清单，再决定如何处理历史孤立文件，不直接批量删除。

**验收**：模拟清理失败后任务仍保留；应用重启可继续重试；重复执行安全；仍被引用的头像和根目录外文件不会删除。若增加表结构，用 V5 或后续版本追加迁移，不修改 V1–V4。

## 6：按数据和真实需求决定的优化

现有列表已是计数加关联分页两条 SQL。先用明确规模的虚构数据测量按姓名、工号、院系和状态查询的耗时与查询计划，记录环境及冷热缓存条件。包含匹配的搜索是否需要索引或查询方式调整，应以 MySQL `EXPLAIN` 和结果等价性验证决定；没有瓶颈时不先引入 Redis、搜索引擎或缓存。

院系管理员、数据范围、导入导出、SSO 和业务审批，先确认谁使用、可看哪些数据、谁负责维护以及是否存在真实流程；再设计服务端规则。当前项目没有真实学校交付证据，不将这些功能提前写入项目描述。
